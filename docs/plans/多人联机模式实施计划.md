## 0. 目标与硬约束速记

为多人游戏实况视频做字幕：12 个样式分组（各带说话人、头像与完整 ASS Style）、三条可同时显示的字幕轨、按槽位排版与单块偏移、头像预览与烧录。

贯穿所有阶段的约束（下文每节都会回到这几条）：

| # | 约束 | 本计划的落实方式 |
|---|---|---|
| C1 | 默认关闭、工程级开关；关闭时行为/快捷键/导出与上游完全一致 | 唯一开关 `multiplayer.enabled`；所有挂钩先判 `MaweMultiplayer?.isEnabled()`，否则走原路径。新增「关闭态等价」回归测试（§5） |

### 1.6 轨道模型现状（决定 B 的方案）

- 编辑器里「轨」是硬编码的三种 kind：`main` / `extension` / `overlay`。`editor-state.js` L6 选区只认这三个键（未知键直接抛错）；`'overlay'` 字面量在 30 个文件出现 153 次，`extension` 类似。
- 三条数组的语义：`segments`（主轨，轨内不重叠）；`overlay_track.segments`（独立轨，可与主轨任意重叠、轨内不重叠、**无绑定**）；`multi_subtitle.tracks[0].segments`（副轨，可有可无的 1:1 绑定）。
- 波形：叠加轨与主轨**画在同一 lane**（`cue-blocks.js` L396-471，cover 模式），副轨有独立 lane。
- ASS：三条数组已分别生成 `main` / `overlay` / `extension` 角色进入同一份排版计划。

### 1.7 样式库窗口

`editor-wiring-ass-manager.js`：选择对象 `assStyleManagerSelection = {kind:'style'|'profile', id}`（L5）；`renderAssStyleList()` L101、`selectedAssStyle()` L52、`syncAssStyleForm(style)` L186（对任意 style 对象生效）、`updateAssStyleField()` L163（写回样式库）、`duplicateAssStyle()` L334、列表右键 `showAssListContextMenu()` L501。样式库是**本机配置**（`ass-styles.json` / localStorage），最多 64 个样式。

### 1.8 说话人与颜色

- `maw/speaker.py` `apply_speaker_colors()` L34：ASR 的 `speaker` 按首次出现顺序写成 5 色 `color/color_ref`，超过 5 人取模回绕。

## 3. 设计要点

### 3.1 分组、cue 表与对账

- 12 个分组固定存在（id `g01`–`g12`，与快捷键一一对应），默认样式由 `ASS_DEFAULT_ASS_STYLE` 派生、主色取 12 色板（前 5 色沿用 `maw/colors.py` 五色）。
- 每条字幕的多人属性（分组、槽位覆盖、偏移）存在 `multiplayer.cues`，键为 `"<轨>/<段 id>"`（段 id 是上游已有的稳定 ID）。
- **分组解析优先级**：cue 表显式分组 → `speaker_map`（ASR speaker → 组）→ `color_map`（字幕颜色 → 组，默认 黄/绿/红/紫/蓝 → 1–5）→ 第 1 组（实施时调整：ASR 超过 5 人时颜色会回绕，说话人映射更精确）。这样上游编辑过的工程（cue 表里有失效键、或新段没有条目）也能稳定降级。
- **对账**（一个挂钩代替逐个改拆分/合并函数）：每次命令提交后比较前后各轨段 id 集合——消失 1 条、新增若干条且时间落在原范围内 → 新段继承原条目（拆分）；多条消失、新增 1 条覆盖它们 → 继承最早一条（合并）；删除则清理条目。上游未来新增的编辑操作也能被覆盖。
- ASR 自动分配：按 speaker 首次出现顺序写入 `speaker_map`（最多 12 人，超出回落第 1 组并提示），而不是回绕到 5 色。

### 3.2 三轨方案（B 的轨道合并问题 → 见决策 D1）

三个候选：

| 方案 | 轨 1 / 2 / 3 | 优点 | 代价 |
|---|---|---|---|
| **甲：借用现有三条数组**（推荐） | 主轨 `segments` / 叠加轨 `overlay_track` / 副轨 `multi_subtitle.tracks[0]`（多人模式下停用绑定语义） | 选区、拖动、拆分合并、列表、撤销、ASS 三角色**全部现成**；上游文件改动最少；上游版本打开工程时三轨内容仍可见、可导出 | 多人与双语互斥（同一工程不能同时有翻译副轨）；同时显示上限 3 条；叠加轨需在多人模式下拆出独立 lane；副轨的「绑定/成对选中/双语导出」要在多人模式下屏蔽 |
| 乙：独立并存 | 主轨 / `multiplayer.tracks[0]` / `multiplayer.tracks[1]` | 语义干净；可与双语、叠加轨共存；轨数可扩展到 4+ | 要新增 kind，触及约 30 个上游文件（选区、波形、拖动、列表、键盘、拆分、合并、导出），**合并上游冲突面最大**，工作量约为甲的 3–4 倍 |
| 丙：统一重构为通用 N 轨 | 把 overlay/extension 改造成通用轨 | 长期最整洁 | 重写上游核心，违背 C2，不考虑 |

**已定：采用方案甲**（D1），理由：fork 的首要约束是长期跟上游合并（C2），甲把新增复杂度集中在「多人开启时的分支」上；游戏实况场景同时需要翻译副轨的概率低。若您需要「真正 4 人同时开口」或「多人 + 双语同时存在」，则应选乙（见 D2）。

方案甲的具体做法：
1. 开启多人模式前检查副轨：已有绑定或非空的双语副轨时提示并拒绝（或由用户确认转为轨 3，解除全部绑定）。
2. 多人开启时：`multiSubtitleVisible()` 挂钩返回 true 以显示轨 3 lane，但不改写 `multi_subtitle.enabled`；绑定类操作（G/Shift+G/H、成对选中、绑定时自动对齐、双语合并导出）在入口处被 `[multiplayer]` 守卫屏蔽。
3. 叠加轨在多人开启时由 `cue-blocks.js` 的挂钩改为画在独立 lane（复用副轨 lane 的布局计算），不再 cover 主轨。
4. 关闭多人模式：数据原样保留，三条数组按上游语义显示（轨 2 = 叠加、轨 3 = 副轨），满足「关闭时现有轨不受影响」。

### 3.3 共享排版模块 `multiplayer-layout.js`

输入：`buildAssPayload` 已准备好的 stackItems（每项补充 `track`、`group`、`slot`、`offset`、`avatar`）、槽位表、头像样式、PlayRes、注入的测量器。输出：

```text
{ slices: [ { start, end, items: [ {…stackItem, alignment, offset:{x,y}, absolute:true, rect} ], pieces:[{start,end}] } ],
  avatars: [ { start, end, group, assetId, x, y, w, h, layer:'below'|'above', opacity, shape, radius, shadow } ],
  diagnostics: [ … ] }
```

- 产出的每个文字项都是 `absolute: true`——上游导出（`ass-export.js` L419-425）与 `assStackFrame`（L440）已经支持绝对定位项，因此导出 `\an…\pos` 与 Canvas 锚点无需新代码路径。
- **整体框居中**：框宽 = 头像宽 + 间距 + 文字宽（头像在左/右）或 max(头像宽, 文字宽)（头像在上）；框中心 x = 槽位中心 x + 单块偏移。
- **文字锚定在贴近头像的一侧**（对您规则的细化）：头像在左 → 文字 `\an1` 左锚定于「头像右缘 + 间距」；头像在右 → 文字 `\an3` 右锚定于「头像左缘 − 间距」；头像在上 → 文字 `\an2` 居中、顶部紧贴头像下缘 + 间距。这样浏览器与 libass 的测宽误差只会让整体中心略偏，**头像与文字之间的间距永远精确**。若头像在右仍用左锚定，间距会吃进测宽误差。
- 槽位：每个槽位是 PlayRes 高度的比例（文字块底边基线），轨默认槽位可配，单块可用 `Alt+↑/↓` 覆盖、可加 `(x,y)` 偏移（PlayRes 比例，分辨率无关）。
- 同一切片中两个块落在同一槽位（覆盖导致）时，后开始的块按实测高度向上让位并给出提示；超宽按分组样式 `marginL/R` 折行。
- 多人模式下忽略 profile 的 `\move`（位置由槽位决定，给提示）；`\fad` 保留；`\t` 的几何类标签（字号/缩放）会让头像与文字比例失配，按上游「不支持即诊断」的惯例提示关闭。

### 3.4 头像预览

- 资源：分组引用 `assets` 中的图片（D5 决定存储方式）。Canvas 侧解码一次、按（资源, 尺寸, 形状, 阴影）缓存离屏位图。
- 绘制顺序：文字后层头像 → `drawTrack` 文字 → 文字前层头像，与烧录滤镜链顺序一致。
- 预览仅在 ASS 模式（Canvas）下精确呈现（D6）。

### 3.5 头像烧录与实际帧

- `maw/multiplayer_avatars.py`：
  - `prepare_avatar_png(asset, w, h, shape, radius, opacity, shadow) -> Path`：Pillow 生成带透明度、阴影、圆角/圆形裁切的 RGBA PNG；同参数复用同一文件。
  - `build_filter_complex(placements, ass_name, video_label) -> (inputs, graph)`：`[0:v]` → 文字后头像 overlay 链（`enable='between(t,a,b)'`）→ `ass=filename=…` → 文字前头像 overlay 链 → `[vout]`。同一图片、同一坐标的多次出现合并为一个 overlay，`enable` 用 `between()+between()` 求和，控制滤镜数量。
- 实际帧：编辑器只发送当前时刻活跃的头像落点（几条），服务器单帧渲染走同一 `build_filter_complex`，保证「实际帧 = 烧录」。
- 烧录：头像计划随 ASS 传递（D7）。

## 6. `multiplayer` 数据结构草案

### 6.1 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema` | string | `maw.multiplayer.v1`；未知版本时只读保留、不启用 |
| `enabled` | bool | 工程级开关，缺失为 `false` |
| `groups` | array(12) | 每项 `{id, name, speaker, avatar, style, avatar_style?}`；缺项按默认补齐，多余项忽略但保留 |
| `groups[].style` | object | 与样式库条目同形的完整 ASS Style（`normalizeAssStyle` 形状，字号按 1080p 参考，导出时按 PlayResY 换算）；阴影色 = `backColor`（ASS 在 BorderStyle=1 时以 BackColour 作阴影色） |
| `groups[].avatar` | string\|null | 指向 `assets` 的资源 id |
| `groups[].avatar_style` | object | 可选，覆盖 `avatar_defaults` 的任意子集 |
| `color_map` | object | 字幕颜色名 → 分组 id，默认黄绿红紫蓝 → g01–g05 |
| `speaker_map` | object | ASR opaque speaker id → 分组 id |
| `tracks` | object | 轨 → `{label, slot}`；键为 `main` / `overlay` / `extension`（方案甲） |
| `slots` | array | `{id, y}`；`y` 为文字块底边占 PlayResY 的比例；默认 3 个，允许 1–5 个（为可选第 6 阶段预留） |
| `cues` | object | `"<轨>/<段 id>"` → `{group?, slot?, offset?:{x,y}}`；失效键保留到下次对账清理 |
| `avatar_defaults` | object | `position`(left/right/top)、`gap_em`、`size_em`、`opacity`(0–100)、`shadow{color,opacity,blur,x,y}`、`shape`(circle/rounded/none)、`radius`(0–0.5)、`layer`(below/above) |
| `assets` | object | 资源 id → `{mime, width, height, data}`（D5） |

- **接入**：`serve.py` `render_ass_frame_png` 在 ASS 带头像节时改用同一函数（缺 Pillow 时退回纯文字并给出提示）；`postprocess_ffmpeg.py` `run_burn_subtitles` 读取 ASS 头像节自动改用 `filter_complex`（缺 Pillow 时报 `MediaToolError`，不生成缺头像的视频），无头像节时命令与上游逐字一致（有单测）。没有改 `BurnSubtitleRequest`、`gui_web.py` 与 `postprocess_pipeline.py`：头像计划随 ASS 文件自带，Launcher 烧录自动生效。

### 9.6 D11 决策（2026-10-15）：发布包打入 Pillow

| # | 问题 | 选项 |
|---|---|---|
| D11 | 发布包里的头像烧录 | a 发布包恢复打入 Pillow（改 `MAW.spec` 排除表、主依赖与两处上游契约测试，约 +10 MB，合并上游时这几行可能冲突）/ b 头像预处理改为纯 FFmpeg 滤镜实现（无新依赖，但偏离「用 Pillow 预处理」的原始要求，阴影与抗锯齿需重新校准）/ c 冻结包调用已安装的 OCR 运行时（含 Pillow）做预处理（不改主包，但要求用户先装 OCR 运行时） |

**结论：选 a**（维护者确认）。依据：上游 1.4.0-beta.6 把 Pillow 移出主程序，是因为当时只有 OCR 用到它，契约测试的本意是「主包不含 OCR 依赖」；多人头像烧录是与 OCR 无关的新用途。实施：

- `pyproject.toml` 主依赖加入 `pillow>=10.0.0`；`uv.lock` 只手工增加 2 行（项目依赖与 requires-dist），`uv lock --check` 通过，避免新版 uv 重写整份锁文件造成与上游的大面积冲突。
- `MAW.spec` 的冻结排除表去掉 `"PIL"`（附注释），PyInstaller 会跟随 `maw.multiplayer_avatars` 中的导入打包 Pillow；OCR 运行时的 `package_dirs` 不变，仍自带 Pillow。
- `tests/test_packaging_contract.py`：排除表断言去掉 `PIL` 并改为断言不再排除；主依赖断言由「不含 Pillow」改为「含 Pillow」，RapidOCR / ONNX Runtime / numpy 仍断言不在主依赖、OCR 依赖组保持原样。两处均标 `[multiplayer]`。
- 未执行完整 PyInstaller 打包；发布前需在打包产物中实测一次头像烧录。
